# Cherry Novel Tavern｜AI 小说创作与酒馆兼容工作台

> 基于 Cherry Studio 的长篇小说创作工作台，兼容酒馆类提示词资产。它把聊天模型、知识库、章节编辑器、世界书和人物档案组合成一条可检查、可回退的写作流程。

> 文档版本：v0.2  
> 更新时间：2026-09-29  
> 状态：项目定位与开发基线

**关键词：** AI 小说创作、AI 写作、小说续写、长篇小说、网文写作、章节写作、小说大纲、角色卡、人物卡、世界观、世界书、World Info、Lorebook、SillyTavern、酒馆、TavernAI、角色扮演、提示词工程、Prompt、知识库、RAG、Cherry Studio、Novel Studio、Novel Writing、AI Roleplay

## 1. 我们要做什么

Novel Studio 不是一个单纯的聊天窗口，也不是把酒馆界面原样搬进 Cherry Studio。它的目标是让作者围绕一部小说持续工作：建立作品资料，规划章节，维护人物和世界观，调用模型讨论或生成正文，并能在生成前看到模型实际收到的上下文。

项目以 Cherry Studio 为底座，复用它已经具备的能力：多 Provider、多模型、流式输出、消息编辑、知识库检索、文件处理、提示词管理和本地数据层。小说功能作为独立模块加入，不改变普通聊天和其他工具的使用方式。

## 2. 产品边界

### 2.1 第一目标

1. 让作者能建立一部小说，并管理章节、实体、关系和时间线。
2. 让模型根据明确选择的前文、世界书、人物卡和知识库资料进行讨论、续写、润色和审计。
3. 让作者能在生成前查看、修改和保存完整提示词。
4. 让每次生成都能回退到草稿、历史消息或另一个分支。

### 2.2 明确不做的事

- 不把外层目录中的个人小说、JSON、截图或其他素材放进公开代码仓库。
- 不把 API Key、个人数据或运行时数据库提交到 Git。
- 不默认把小说正文同步到云端；是否发送以及发送给哪个模型由用户的 Provider 设置决定。
- 不把生成结果视为事实。人物状态、时间线和世界书的 AI 更新都必须经过用户查看或确认。

## 4. 领域模型

小说功能使用 Cherry Studio 现有 SQLite + Drizzle + Data API 数据层，不另建一套用户目录数据库。

- **Novel**：作品标题、简介、创作模式和更新时间。
- **Chapter**：章节标题、正文、提纲、状态、顺序和字数。
- **NovelEntity**：角色、地点、道具、组织或其他实体；角色字段兼容 ST Character Card 常用字段，同时保留叙事档案字段。
- **NovelEntityRelation**：实体之间的关系类型和描述。
- **TimelineEvent**：剧情、转折、揭示、冲突、日常等事件，可绑定章节和参与者。
- **Worldbook / WorldbookEntry**：世界书及其键词、内容、位置、深度、优先级、启用状态等。
- **StPreset**：ST 预设的原始 JSON 快照及内部解析结果。
- **NovelChatSession**：章节、提示词资产、前文范围、历史轮数和参考模式的会话配置。

外部导入文件和内部可编辑记录采用双轨制：导入的 ST JSON 保留原始快照，运行时使用内部解析数据；只有用户主动导出时才重新生成标准 JSON。

## 5. 核心工作流

### 5.1 新建作品

支持四类入口：

1. **结构化创作**：从一句话灵感开始，经过雪花法逐步形成作品、角色、分卷和章节计划。
2. **旧稿重塑**：导入 TXT/DOCX，先拆章和分析，再由用户确认人物、设定、事件、关系和时间线。
3. **自由创作**：建立空白作品后直接进入写作台。
4. **项目导入**：导入 Novel Studio 的项目 JSON 备份，恢复资料和章节结构。

### 5.2 一章写作

1. 选择当前章节、模型、前文回溯范围和对话历史范围。
2. 选择世界书、ST 预设、角色实体、时间线和知识库参考模式。
3. 输入写作指令，先预览组装后的系统消息和用户消息。
4. 流式生成正文、讨论结果或大纲；可停止、重写、编辑和保留多个版本。
5. 用户采纳后写入章节草稿，再决定是否更新人物卡、时间线或世界书。

### 5.3 审计与回退

审计至少覆盖：人物状态、时间顺序、空间位置、世界规则、前文事实、伏笔、节奏和文风。审计结果是建议，不直接覆盖正文。正文、提示词资产和会话都应保留可回退的版本边界。

## 6. 提示词与上下文组装

组装器是本项目的核心基础设施，输入来源至少包括：

1. 系统写作规则和用户可编辑的写作上下文。
2. ST 预设的 `prompts` 与 `prompt_order`。
3. 角色卡、世界书和时间线。
4. 当前章节、选定回溯章节和会话历史。
5. 知识库召回片段和可选网络搜索结果。
6. 当前写作指令。

组装器应输出两份结果：

- 发送给模型的标准 `system/user/assistant` 消息数组。
- 面向用户的来源报告，说明每段内容来自哪个章节、实体、世界书条目、知识库片段或模板。

第一阶段兼容的 ST 能力：

- `prompts`、`prompt_order`、启用/禁用条目。
- 常用宏，如 `{{char}}`、`{{user}}`、角色描述和场景。
- 世界书关键词、正则、常驻条目、插入位置、深度和顺序。
- 常见 system/user/assistant 注入位置。

不支持或有差异的字段必须在导入和预览时显示警告，不能静默丢弃。

## 7. 公开项目形态

GitHub 公开仓库只包含内层代码目录及其文档，不包含外层的小说文本、JSON、截图和本地运行数据。公开前应检查：

- `.env`、密钥、令牌和数据库没有进入提交。
- `node_modules`、`dist`、`out` 等生成目录没有进入提交。
- Cherry Studio 原始 `LICENSE`、作者信息和来源链接完整保留。
- Novel Studio 的新增代码、文档和示例不包含个人小说内容。

本项目基于 Cherry Studio 的 AGPL-3.0 代码，后续公开仓库应继续遵守上游许可证和贡献者要求。仓库名称、Fork 或独立仓库方式在实际上传前单独确认。

## 8. 开发路线

| 阶段 | 目标 | 验收标准 |
|---|---|---|
| A 基线整理 | 统一小说入口，区分正式功能与 M10 实验功能 | 路由、侧边栏、文档和数据类型描述一致 |
| B 组装器稳定 | 固定 ST 预设、世界书、实体和章节的组装契约 | 预览消息与发送消息相同，关键分支有单测 |
| C 写作闭环 | 章节编辑、流式生成、采纳、版本和回退 | 完成一章端到端写作并可恢复草稿 |
| D 资料维护 | AI 提取人物、时间线、关系和世界书，均需用户确认 | 旧稿导入结果可编辑、可拒绝、可重复运行 |
| E 长篇增强 | 卷级规划、上下文增量提取、多轮审计和分支 | 长上下文下 Token 预算、来源和回退可见 |
| F 公开发布 | 清理私有素材，补充安装、贡献、隐私和示例 | 仓库可独立阅读、安装和运行 |

每个阶段都应先写清数据契约和可验证的验收路径，再实现界面。测试重点是纯组装函数、数据迁移、流式中止、导入导出往返和敏感数据隔离。
